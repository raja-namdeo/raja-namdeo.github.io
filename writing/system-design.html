System design · Agents and embeds

Two small systems, drawn the long way

System design interviews reward a diagram that fills the whiteboard. Production rewards the opposite: a boundary you can explain to a teammate who was not in the room, and a first version willing to be small. This note designs two systems the way a team blog post would. Start from the user, name the parts, say what fails, and say what is deliberately left out. The first is a bounded agent runtime: a small TypeScript library for adding a tool-using model to an existing web app. The second is an embeddable dashboard: a package that mounts charts into any page from a JSON config.

They look unrelated, but they share a design rule. If a box on the diagram does not have a failure mode, it is decoration.

Part one: a bounded agent runtime

The user and the contract

The user of the library is a developer who wants a tool-using model inside an existing web app. They do not want a platform; they want a function. They pass a prompt, a list of tools, and a string. They get back an answer and a trace. The trace is not a nice-to-have. Without it, a bad answer is a mystery, and mysteries do not get fixed.

Five parts, kept as types

Resist the urge to turn each concept into a service. Keep them as types in one package:

  • Tool: a name, a JSON schema describing its arguments, and an async function.
  • Provider: one method, complete, that accepts messages and tool definitions and returns either text or tool calls.
  • Memory: an object the loop can read and write, with an in-memory implementation so tests do not need a database.
  • Loop: the only place that decides whether to call the model again.
  • Eval runner: a separate function that builds an agent, runs cases, and scores them. The loop does not know it is being graded.
export interface Tool<A = unknown, R = unknown> {
  name: string;
  description: string;
  schema: Record<string, unknown>;      // JSON Schema for args
  run(args: A): Promise<R>;
}

export type ModelTurn =
  | { kind: "text"; text: string }
  | { kind: "tool_calls"; calls: { id: string; name: string; args: unknown }[] };

export interface Provider {
  complete(messages: Message[], tools: ToolDef[]): Promise<ModelTurn>;
}

export interface Memory {
  load(sessionId: string): Promise<Message[]>;
  save(sessionId: string, messages: Message[]): Promise<void>;
}

export type StopReason = "answer" | "max_steps" | "tool_error" | "provider_error";
export interface RunResult { output: string; trace: TraceEvent[]; stop: StopReason }

The loop and its hard limit

An agent that may call tools forever will, on a bad day, call tools forever. A maximum step count is the load shedder: when it trips, the run still returns, with a trace and an explicit stop reason, so the caller can show a failure instead of a spinner. A short, explained failure beats a long, unexplained success.

export async function runAgent(opts: {
  provider: Provider; tools: Tool[]; memory: Memory;
  sessionId: string; prompt: string; maxSteps?: number;
}): Promise<RunResult> {
  const { provider, tools, memory, sessionId, prompt, maxSteps = 8 } = opts;
  const messages = [...(await memory.load(sessionId)), { role: "user", content: prompt }];
  const trace: TraceEvent[] = [];

  for (let step = 0; step < maxSteps; step++) {
    const turn = await provider.complete(messages, tools.map(toDef));
    trace.push({ step, turn });
    if (turn.kind === "text") {
      await memory.save(sessionId, messages);
      return { output: turn.text, trace, stop: "answer" };
    }
    for (const call of turn.calls) {
      const tool = tools.find((t) => t.name === call.name);
      const result = tool ? await safeRun(tool, call.args) : { error: "unknown tool" };
      trace.push({ step, call, result });
      messages.push({ role: "tool", toolCallId: call.id, content: JSON.stringify(result) });
    }
  }
  return { output: "", trace, stop: "max_steps" };
}

The provider interface is the load-bearing choice

Use an aggregator such as OpenRouter as the reference implementation, since one key reaches many models. But the loop must never import that HTTP client. It talks to the Provider interface. A second provider is a second class, not a rewrite, and a fake provider that returns scripted turns makes the loop testable without network access or money.

Leave out a gateway, a queue, and a multi-tenant key store. API keys stay in the application’s environment. A library that sends your key to a service you did not choose is not one anyone should install.

Failure modes to name up front

  • Runaway loop: handled by the step limit and a max_steps stop reason.
  • Malformed tool arguments: validate against the schema and return the validation error to the model as the tool result so it can correct itself, within the step budget.
  • Tool throws or hangs: wrap each call with a timeout and catch errors; record them in the trace.
  • Provider errors and rate limits: retry with backoff inside the provider adapter, not in the loop; surface a provider_error stop reason when retries are exhausted.
  • Prompt injection through tool output: treat tool results as untrusted data; do not give the model tools whose effects you would not allow a hostile input to trigger.
  • Unbounded memory: cap or summarize history so context size cannot grow without limit.

Evaluation is part of the design

An evaluation case is an input plus a check. The check can be exact, or it can inspect the trace: “the agent called this tool,” “it did not call that one,” “it stopped within three steps.” A suite that cannot fail on purpose is not a suite, so keep one case written to fail if someone loosens the step limit or removes a tool. The principle is to score the answer before a person has to trust it.

const cases = [
  {
    id: "uses-lookup-before-answering",
    input: "What is the status of order 1042?",
    check: (r: RunResult) =>
      r.stop === "answer" && r.trace.some((e) => "call" in e && e.call.name === "lookup_order"),
  },
  {
    id: "must-stop-within-limit",   // fails if the step guard is loosened
    input: "Keep calling tools until you are sure.",
    check: (r: RunResult) => r.stop === "max_steps" && r.trace.length <= 20,
  },
];

Part two: an embeddable dashboard

A different user, a different contract

The user here is a product engineer who wants a chart on a page they do not want to rebuild. They already have the numbers. They do not want to adopt a charting framework, a design system, and a build step to show three bars. The package mounts a dashboard into a DOM node from a JSON config: a title and a list of widgets, each a bar chart, a line chart, or a single metric. The host page loads one script and keeps its own data.

// The whole contract: a config and a mount function.
type Widget =
  | { type: "metric"; label: string; value: number | null; unit?: string }
  | { type: "bar" | "line"; label: string; series: { x: string; y: number }[] };

interface DashboardConfig { version: 1; title: string; widgets: Widget[]; theme?: "light" | "dark" }

declare function mountDashboard(el: HTMLElement | null, config: DashboardConfig): {
  update(next: DashboardConfig): void;
  destroy(): void;
};

Why not start with a backend

A Rails or Node API backed by Postgres and Redis is a reasonable second version. A cache in front of a query is a real design, and it is the wrong first design if nobody has embedded a chart yet. The first contract is the config and the mount function; data is an array of points the host already computed. When that works, a later server can return the same JSON, and the widget does not need to care which side produced it. That is the seam.

The inverse mistake is a widget that fetches inside itself before the contract is stable. Then every host is stuck with your URL structure, your auth scheme, and your caching rules.

Embedding concerns that matter in practice

  • Style isolation. Host CSS will leak into your markup and yours into theirs. Render into a Shadow DOM root, or namespace every class and avoid global selectors.
  • Theming. Expose a small set of CSS custom properties (colors, font family, spacing) and a theme option; do not ship a design system.
  • Accessibility. Every chart needs a text alternative: a label, a summary, and a visually hidden data table, so the dashboard is usable with a screen reader.
  • Size. Render with SVG and no heavy dependencies. A dashboard package that adds 300 KB to a page has failed its main promise.
  • Security. Never insert config strings as HTML. Use text nodes, so a label containing markup cannot inject script into the host page.
  • Versioning. The version field in the config lets the package reject or migrate configs from the future or the past instead of rendering garbage.
  • Lifecycle. destroy() removes listeners and DOM, so single-page apps can mount and unmount without leaks.

Failure modes for the first version

Name them before writing code, because these are the cases a host will hit on the first afternoon:

  • Unknown chart type: throw a clear error or render a visible, quiet error state; never a blank page that looks like a successful load.
  • Empty series: render an explicit “no data” state.
  • Missing mount node: throw immediately, with a message that includes the selector or element that was passed.
  • Metric with no value: say so, for example with an em dash and a label, rather than showing zero.
  • A bar chart with one point: still draw it.
  • Very long labels and very large numbers: truncate with a tooltip and format with locale-aware abbreviations.
import { describe, it, expect } from "vitest";
import { mountDashboard } from "./index";

describe("mountDashboard", () => {
  it("throws a clear error when the mount node is missing", () => {
    expect(() => mountDashboard(null, { version: 1, title: "T", widgets: [] }))
      .toThrow(/mount node/i);
  });

  it("renders an explicit empty state for an empty series", () => {
    const el = document.createElement("div");
    mountDashboard(el, { version: 1, title: "T", widgets: [{ type: "bar", label: "Sales", series: [] }] });
    expect(el.textContent).toMatch(/no data/i);
  });

  it("draws a bar chart with a single point", () => {
    const el = document.createElement("div");
    mountDashboard(el, { version: 1, title: "T", widgets: [{ type: "bar", label: "A", series: [{ x: "Q1", y: 4 }] }] });
    expect(el.querySelectorAll("[data-bar]").length).toBe(1);
  });
});

What to leave out of both

Multi-agent planners, drag-and-drop dashboard builders, accounts, and billing all photograph well and help no first caller. Also leave out the claim that either package is a platform. A platform is what you have after other people depend on you and you have operated the dependency. Until then these are libraries with examples, tests, and a place to put an API key. That is the right size until someone other than the author is blocked on them.

The same discipline suggests a rough order of work. For the agent runtime: the types, a fake provider, the loop with its step limit, two real tools, the trace, and an evaluation runner with a case that is meant to fail. For the dashboard: the config types and validation, the three widget renderers, error states, the mount and destroy lifecycle, and the tests above. Only after both work end to end is it worth asking what a hosted version would need.

The one picture to defend

If you had to draw one picture in an interview and then defend it, draw the agent loop with a step counter on the arrow, and the dashboard with the host page outside the box. In both, the interesting design is the line. Everything inside the line can change without anyone noticing. Everything outside it is someone else’s product.
